# 决策：镜像证据与可生长产品代码分离

日期：2026-10-22

## 背景

原站可通过 Playwright 完整采集，但未发现明确的源代码再发布许可证。当前 GitHub 仓库是公开的。镜像包含原站 HTML、JS、CSS、字体、图像和课程文案；直接提交这些文件会把未经确认的第三方内容发布到公开仓库。原始 bundle 也不适合直接作为长期维护的业务源码。

## 备选方案

- 方案 A：直接把 `mirror/` 或 `src/` 提交到公开仓库，最快，但会混淆证据与产品源码，并带来未确认的内容再发布风险。
- 方案 B：直接改写原始 bundle，初期看似改动少，但难以审计字节变化，也会把 minified 结构固化成长期架构。
- 方案 C：镜像、port、字节切片和独立 scaffold 分层，证据可复核，产品代码可独立生长。

## 推导原因

选择方案 C。原站没有发现明确许可证；原始 bundle 中的 UI、课程数据、语言映射和情景模拟耦合在一起；`Run sketch` 也不是通用 C++ 执行器。保持证据不可变，才能在后续改写中用可复现的行为测试判断哪些行为被保留、哪些被有意升级。

## 决策

1. `mirror/` 是原始证据，只允许重新采集，不在其中编辑。
2. `port/` 是从 manifest 逐字节复制的本地可运行副本，只用于验证，不作为新产品源码。
3. `src/` 是原始 bundle 的字节保持切片/重组证据；不得在这里做语义重写。
4. 新产品代码放在独立 `scaffold/` 或独立仓库，基于行为规格重新建模，不依赖镜像运行时。
5. `mirror/`、`port/`、`src/`、`probe/` 保持 gitignored；不提交、不推送、不部署原站派生资产，直到用户确认权利边界。
6. 新 scaffold 可以复用通用概念和自行编写的几何/模拟算法，但不直接复制原站完整文案、图片或 minified bundle。

## 后果

- 优点：原站行为证据稳定；产品代码可独立重构；不会把“能运行的镜像”误当作可维护架构；降低误公开第三方内容的风险。
- 成本：本地需要维护镜像、port 和 scaffold 三个不同用途的目录；每次原站更新都要明确是否重新采集，不可自动覆盖新产品代码。
- 重新评估条件：确认原站明确许可证或获得授权；或用户明确决定只在私有环境中继续进行派生复刻。

## 验收

- `verify-mirror` 对原始镜像通过。
- `port/` 的源文件与镜像 manifest 中的字节数和 SHA-256 一致。
- `src/readable/` 的所有分解都能逐字节重组回原始 bundle。
- Git 状态中不出现 `mirror/`、`port/`、`src/`、`probe/` 的文件。
