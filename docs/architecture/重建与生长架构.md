# 从网页镜像到可生长的 Arduino 教学运行时

状态：设计合同已落地第一版 `scaffold/`；`mirror/`、`port/`、顶层 `src/` 是原站证据层，不进入公开 Git。独立产品代码位于 `scaffold/src/`，当前覆盖课程注册、预定义情景模拟、事件流、3D 投影与 UI；真实电气求解、Arduino 解释器和完整课程判卷尚未实现。

## 1. 核心判断

原站是一个程序化 3D 教学应用，不是一个真正的 Arduino IDE。它有 16 个课程和对应的 `sim` 标识，`Run sketch` 把 `lesson.sim` 交给固定情景分支；代码区只展示课程代码，不提供可编辑输入，也没有观察到真正的 C++ 编译/上传路径。其 3D 场景使用 Three.js r186 与 WebGL2，部件状态和动画由 JS 代码生成。

因此，“重生”的目标不应是把一个 130 KB 的主 bundle 美化成另一个大文件，而应将它的行为分解为稳定的数据契约、可插拔的模拟器、可组合的 3D 部件和可测试的 UI 投影。原站镜像是验收参照，不是新产品的运行时依赖。

## 2. 目标运行时分层

```text
课程作者 / lesson module
          │ LessonDefinition
          ▼
LessonRegistry ───── PartRegistry ───── LocaleCatalog
          │                 │                 │
          ▼                 ▼                 ▼
SimulationRegistry     PartDefinition     Stable message keys
          │
          ▼
SimulatorSession ── InputEvent / Clock / Seeded RNG
          │
          ▼
Ordered SimulationEvent stream
          │
          ├──────────────► Circuit/Pin state
          │                      │
          │                      ├──► Three.js SceneProjection
          │                      ├──► Pinout/Inspector projection
          │                      ├──► Code/Trace projection
          │                      ├──► Serial monitor projection
          │                      └──► Progress/Completion projection
          ▼
Deterministic replay + test snapshots
```

运行时只有一个状态事实源。3D 场景、串口监视器、引脚状态和教学步骤都从同一事件流/状态投影得到，不允许每个面板自行维护一套互不一致的模拟状态。

## 3. 对象 / 态射表

| 对象 | 主要职责 | 态射/转换 | 不变量 |
|---|---|---|---|
| `LessonDefinition` | 课程目标、示例代码、部件、接线、参数、模拟器 ID、验收轨迹 | `registerLesson → LessonRegistry` | `id` 全局唯一；课程定义不直接操作 DOM/Three.js |
| `PartDefinition` | 部件 ID、引脚、标签键、几何工厂、检查面板 schema | `instantiatePart → PartInstance` | 引脚 ID 稳定；渲染几何不能改变电气语义 |
| `SimulatorPlugin` | 一类模拟行为的初始化、输入、时间推进、事件输出 | `create → SimulatorSession` | 相同初态、输入、时钟和随机种子产生相同事件轨迹 |
| `InputEvent` | 按钮、旋钮、滑块、键盘或外部传感器输入 | `dispatch → SimulationEvent` | 输入有时间戳和来源，不直接改 UI DOM |
| `SimulationEvent` | 引脚写入/读取、串口输出、部件状态、延时、运行生命周期 | `reduce → RuntimeState` | 事件顺序单调；重放结果可比较 |
| `RuntimeState` | 虚拟引脚、电平、模拟值、部件状态、运行时间 | `projectScene → SceneProjection` | 状态是唯一事实源；投影是可丢弃的派生物 |
| `RuntimeState` | 同一状态 | `projectSerial → SerialProjection` | 串口日志与引脚/场景轨迹属于同一事件序列 |
| `LocaleKey` | 稳定文案身份，如 `lesson.blink.title` | `translate → LocalizedText` | 不以英文原文充当 key；缺失翻译可被检查 |
| `Route` | 语言和页面位置 | `resolve → LocaleBundle + AppRoute` | 路由解析不依赖课程文案内容 |
| `SketchSource` | 可编辑的 Arduino 子集代码 | `run → SketchRuntime` | 只有真实解析/执行器接入后才宣称代码被执行 |

## 4. 规范数据模型

课程数据与执行机制分离。建议以 TypeScript 类型 + Zod（或等价 schema）校验 JSON/TS 模块，避免把业务契约埋进一个 `switch`。

```ts
type LessonDefinition = {
  id: string;
  titleKey: string;
  objectiveKeys: string[];
  partIds: string[];
  wiring: Array<{ from: string; to: string; kind: "digital" | "analog" | "power" | "ground" }>;
  sketch: { language: "arduino-cpp"; source: string };
  simulatorId: string;
  params?: Record<string, number | string | boolean>;
  inspectorKeys: string[];
  expectedTrace: Array<{ atMs: number; event: string; value?: string | number | boolean }>;
};

type SimulatorPlugin = {
  id: string;
  create(context: SimulatorContext, lesson: LessonDefinition): SimulatorSession;
};

type SimulatorSession = {
  start(): void;
  stop(): void;
  dispatch(input: InputEvent): void;
  advance(deltaMs: number): SimulationEvent[];
  snapshot(): RuntimeState;
};
```

`expectedTrace` 是验收合同，不是额外的 UI 文案。测试通过比较轨迹，可以在不截图的情况下判断模拟行为是否改变；视觉测试再单独检查渲染投影。

## 5. Functor 映射与多尺度模型

把整个应用视为从领域模型到多种可视投影的映射：

\[
F: \text{Lesson} \to \text{Scenario} \to \text{EventStream} \to \{\text{Scene},\text{Pins},\text{CodeTrace},\text{Serial},\text{Progress}\}
\]

这里的关键不是数学记号本身，而是组合性：如果同一事件流映射到 3D 引脚和串口日志，事件顺序、时间戳和 pin ID 必须保持一致。改变 UI 布局不应改变模拟结果；更换 3D 几何也不应改变引脚电平。

多尺度结构：

| 尺度 | 对象 | 可复用不变量 |
|---|---|---|
| S0：几何 | Box、Cylinder、材质、灯光 | 单位、坐标系、性能预算 |
| S1：部件 | LED、按钮、旋钮、传感器、舵机 | `partId`、pin 定义、选择语义 |
| S2：电路/运行态 | 虚拟引脚、连线、模拟值、事件 | 电平语义、事件时间顺序 |
| S3：课程 | 目标、代码、参数、场景、验收轨迹 | 课程 ID、模拟器契约、学习目标 |
| S4：课程集合 | 顺序、完成进度、语言、导航 | 稳定路由、稳定翻译键、可恢复进度 |

跨尺度禁止重复定义事实。例如 `D2` 的当前电平只存在于 runtime state；3D 灯光和串口文本都消费该状态，不分别“猜测”电平。

## 6. 模拟器演进策略

先定义统一 `SketchRuntime`/`SimulatorSession` 接口，按能力分两种实现：

1. `ScenarioSimulator`：用于重现当前站点的预定义教学情景。每个插件输出可重放事件，不声称执行任意 C++。
2. `ArduinoSubsetRuntime`：后续可选，解释一部分真实 Arduino 语法/函数，或适配经审查的 AVR 模拟库。只有完成代码输入、解析、执行、错误报告和一致性测试后，UI 才能使用“执行代码”语义。

两者共享事件协议、虚拟引脚、串口投影和 3D 状态投影。这样可以逐课升级，不必重写 UI，也不需要一次性构建完整硬件模拟器。

## 7. 生长性固定点假设

架构达到固定点的可操作判据：新增普通课程只需增加一份课程模块和 locale 项；新增新物理行为时才增加一个模拟器插件；新增部件时增加一个 `PartDefinition` 与几何工厂。以下文件不应因为普通课程增长而变化：全局路由器、课程列表组件、语言解析器、串口面板、事件 reducer 和测试运行器。

如果新增第 17 课仍必须在全局 `switch`、全局 DOM 逻辑和语言解析器中各加一段特判，说明重整化尚未完成。

## 8. 无障碍与可观测性

- 所有可见控件必须有非空 accessible name；禁止 `aria-label=""`。
- 3D 选取必须有稳定的 `partId`，并提供键盘可操作的等价列表/面板；不要把鼠标射线当成唯一入口。
- 当前 `SimulationSession` 持有 seed、输入事件和输出事件，支持导出事件流与 `replay(events)` 精确重放；`runId` 和持久化会话档案留待下一阶段。
- 串口输出、pin 变化、部件动画和教学步骤共享事件时间轴。
- 测试分三层：schema/纯函数单测、确定性轨迹测试、Playwright 路由/键盘/视觉回归。

## 9. 实施路线与门槛

1. **证据层（已完成）**：Playwright 采集、镜像清单、外联清单、12 路由扫查、bundle census。
2. **合同层（已完成 MVP）**：`scaffold/src/content/registry.js` 验证 16 门课程、部件引用和模拟器 ID；课程目前集中定义在 `lessons.js`，尚未拆成每课一个文件或完整 schema。
3. **场景层（已完成 MVP）**：`scaffold/src/scene/board.js` 程序化生成 Arduino 风格测试板与元件，支持鼠标射线选择、键盘可操作的元件列表和相机控制。
4. **模拟层（已完成 MVP）**：`scaffold/src/simulation/` 实现 11 类可复用场景与确定性事件重放，使用虚拟时钟和可播种扰动。
5. **课程与多语言（部分完成）**：16 门课程数据可用；12 个路由可启动，英语与简体中文初版，其余语言明确回退英语。后续要把课程翻译迁移到 `lesson.id + field` 的稳定 message-key 字典，并补充每课的可判卷轨迹。
6. **运行时代码**：如果用户希望代码真正可编辑并执行，再评估 Arduino 子集解释器；在此之前不把模拟上传动画包装成真实编译。
7. **发布门**：视觉/交互/离线测试通过后，再决定公开仓库是否包含新写的 scaffold；原站镜像、切片和原文素材仍不发布，除非确认授权。

## 10. 验收指标

- 课程：每个课程 ID 唯一；每个 `simulatorId` 可解析；每个课程都有至少一个自动化验收轨迹。
- 确定性：固定 seed 和输入下，重复运行的事件轨迹逐项相同。
- 解耦：普通课程新增不修改全局路由、课程列表、locale 解析或 UI 面板代码。
- 可访问性：所有可见按钮/标签都有名称；课程切换和部件选择可用键盘完成。
- 离线：生产资源同源自托管，运行时外联数为 0。
- 回归：12 个路由在目标视口可启动；至少覆盖桌面与移动视口；3D canvas 和面板不互相遮挡关键控件。
- 诚实性：只有接入真实解释器/编译器后才宣称“执行 Arduino 代码”；否则明确标注为情景模拟。
